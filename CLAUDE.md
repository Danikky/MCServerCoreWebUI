# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MCServerCore is a Flask web UI for managing **one or more** Minecraft server processes side by side: start/stop/kill, stream console live, edit `server.properties`, browse online/whitelisted/banned/op players, browse each server's files, manage its core `.jar` (upload or fetch by URL), and create/restore backups. No build step — Jinja2 templates + Bootstrap 5 (CDN) + one hand-written stylesheet, dark-glass/glassmorphism theme.

Comments and flash/error strings in the codebase are in Russian; match that when editing existing strings.

## Running

```bash
./setup.sh     # venv + deps + servers/ folder
./launch.sh    # python3 main.py under the venv
```

Or manually: `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt && python3 main.py`. No test suite or lint config yet (see REVIEW.md's 🟢 section).

Config is environment variables, optionally via a `.env` file (see `.env.example` for the full list — `SECRET_KEY`, `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `ALLOW_REGISTRATION`, `MCSC_DEBUG`/`MCSC_HOST`/`MCSC_PORT`/`MCSC_CORS_ORIGINS`, `MCSC_JAVA_XMX`/`MCSC_JAVA_XMS` — defaults for *new* servers, not global, `MCSC_MAX_UPLOAD_MB`), all read in `app/config.py`. First admin is created once (only if the `users` table is empty) with a random password printed to stdout unless `ADMIN_PASSWORD` is set.

Each managed Minecraft server lives under `servers/<slug>/` (git-ignored, `slug` auto-generated from its name at creation) — its jar/launch script, `server.properties`, `eula.txt`, `usercache.json`, `whitelist.json`, `ops.json`, `banned-players.json`, and a `backups/` subfolder that `ServerManager` creates on demand. Servers are created from the UI (`/servers`), not by hand-placing a folder — the core `.jar` itself can be dropped in either through the UI (`/servers/<id>/core` — file upload or paste a direct download link) or manually copied into `servers/<slug>/` (autodetected the same way either way).

See `DEPLOY.md` for local-vs-prod setup (systemd, nginx+WebSocket, TLS) and `REVIEW.md` for the running audit/roadmap — check its ✅/pending markers before assuming something is (or isn't) already fixed.

## Architecture

App-factory Flask app under `app/`, thin `main.py` entrypoint. **Multi-server**: one panel manages N independent Minecraft server processes; almost every route is scoped under `/servers/<int:server_id>/...`.

- **`app/config.py`** — `Config` class, all settings read from `os.environ` in one place.
- **`app/extensions.py`** — the shared `db` (Flask-SQLAlchemy), `login_manager`, `csrf` (Flask-WTF), `socketio` instances, created here unbound and initialized on the app in `create_app()` (avoids circular imports between models/blueprints and the factory).
- **`app/models.py`** — `User` (role: `"admin"`/`"viewer"`, `user.is_admin` property), `Server` (one row per managed Minecraft server — `name`, unique `slug` used as its folder name under `servers/`, `java_xmx`/`java_xms`; `create_server(name, ...)` generates a unique slug; plus `public_visible`/`public_name`/`public_version`/`public_ip`/`public_description`/`public_contact` — what the public `/status` page shows, hand-entered by admin on the core page, **defaults hidden** (`public_visible=False`) and independent from the internal `name`/real IP; `public_contact` renders as a link only if it starts with `http(s)://`, otherwise as plain text — no URL validation beyond that), `ConsoleLine` (persisted console history, **has `server_id`** — always filter by it, history is per-server). `ensure_first_admin()` creates the first admin once, only if the `users` table is empty.
- **`app/decorators.py`** — `with_server` (resolves `<int:server_id>` from the URL via `current_app.server_registry` into a `ServerManager`, stores it on `g.server`, 404s if the `Server` row doesn't exist — put this on every server-scoped route) plus the role decorators: `admin_required` (whole route admin-only) and `admin_write_required` (GET open to any logged-in user, any other method admin-only). Viewers can see console/status/players/settings but can't run commands, edit anything, or touch the file manager/backups/core (those are `admin_required` entirely — even browsing a server's files can leak plugin config secrets).
- **`app/fs_utils.py`** — pure filesystem helpers, no Flask/DB dependency: `return_main_dir()` (repo root), `safe_join(allowed_root, path)` (resolves and enforces containment, raises `PathEscapeError` — this is what stands between the file manager/backups/core/editor and path traversal), `read_text`/`write_text` (text file editor backend — 2 MB cap, UTF-8-only). **Convention that matters**: if `path` passed to `safe_join`/`rename`/`delete`/`make`/`get_dir`/`read_text`/`write_text` is relative, it's resolved against `return_main_dir()` (repo root) — *not* against `allowed_root`. So every caller that means "a path inside this server's folder" must build the absolute path itself first via `fs_utils.under(server.path, subpath, ...)` before calling into `fs_utils` — see `app/routes/files.py`/`editor.py` for the pattern. Getting this wrong silently resolves against the wrong root (caught and fixed once already — see REVIEW.md).
- **`app/server_manager.py`** — `ServerManager`, **one instance per `Server` row**, constructed from that row (`self.id`/`self.name`/`self.slug`/`self.java_xmx`/`self.java_xms`, `self.path = servers/<slug>/`). Owns that server's subprocess:
  - `start_server()` autodetects the most-recently-modified `.jar` in its folder, falling back to a `.sh`/`.bat` launch script, and spawns it with `subprocess.Popen` (stdin/stdout piped).
  - A daemon thread (`get_console_output`) tails stdout line-by-line, persists each line to `ConsoleLine` tagged with `self.id` (via `self._log`, which pushes a Flask app context since it runs off the request thread), runs `console_event_check` (auto-accepts the EULA and restarts on first boot; regex-matches `"<name> joined/left the game"` to maintain `self.online` under `self.online_lock`), and emits it over the `/server` SocketIO namespace **to room `server-<id>`** — the browser must `emit('join', {server_id})` first (see `control_panel.html`) or it gets nothing; this is what keeps multiple servers' live consoles from bleeding into each other.
  - `send_command_direct()` writes to the subprocess's stdin; `kill_server()` does SIGTERM then SIGKILL.
  - `status` property — `"offline"`/`"starting"`/`"running"`/`"restarting"`, used by both the admin nav badge and the public `/status` page. `"starting"` vs `"running"` is decided by `self.ready`, flipped to `True` when a console line matches `Done (` (vanilla/Paper/Purpur/Fabric's "world loaded" message — `_DONE_RE`), reset to `False` at the top of `start_server()`. `restart_server()` spawns a daemon thread (`_do_restart`) that sends `stop`, polls up to 30s for the process to exit on its own before force-killing, then calls `start_server()` again — `self._restarting` stays `True` (status pinned to `"restarting"`, not blipping through `"offline"`/`"starting"`) for that whole span, cleared only once the *new* process hits `Done (`. Don't call `_do_restart` directly or block on it from a request handler — it's meant to run detached.
  - `save_uploaded_core()` / `fetch_core_from_url()` / `delete_core_file()` / `list_core_files()` manage the `.jar` — upload validates the `.jar` extension via `secure_filename`; URL fetch only allows `http`/`https`, streams with a size cap (`MAX_CORE_BYTES`), and is trusted input by design (admin-only, same threat model as the console — see REVIEW.md on why this isn't hardened against SSRF).
  - Player/property/backup operations shell out to `app/fs_utils.py` or read/write `server.properties`/JSON files directly, all resolving paths through `safe_join` scoped to `self.path` (or `self.path/backups`) — never trust `path`/`item`/`name` from a request without it.
  - `run_player_command(command, username)` — op/deop/kick/ban/pardon/whitelist-remove. Sends `"<command> <username>"` to stdin like any other command, then *polls* (up to 1.5s, 100ms interval, returns as soon as satisfied) the relevant on-disk state (`ops.json`/`banned-players.json`/`whitelist.json`/`self.online`) for confirmation instead of a blind `sleep()` — Minecraft applies these asynchronously, so reading right after sending races the write. `app/routes/players.py` validates `command` against a fixed allow-list and `username` against `^[A-Za-z0-9_]{1,16}$` *before* this ever gets called — those came from an HTML form field, don't assume they're a real Minecraft username or one of the five expected verbs. Skipping either check was the root cause of a real bug (action landing on the wrong player) — see REVIEW.md 🟠 #14 before touching this code.
- **`app/server_registry.py`** — `ServerRegistry` (`app.server_registry`), lazily creates and caches one `ServerManager` per `Server.id` for the process's lifetime. `get(id)` creates-if-missing (and touches disk — `os.makedirs`); `peek(id)` reads the cache without creating (used by the servers list to show status without instantiating managers for servers nobody has opened yet); `forget(id)` drops the cache entry after a `Server` row is deleted.
- **`app/routes/`** — one blueprint per feature area: `servers` (`/servers` — list/create/delete `Server` rows, the post-login landing page), `console` (also handles `restart`), `players`, `settings`, `files`, `editor` (`/servers/<id>/edit/<path:subpath>` — view/edit a text file in-browser, `admin_required`, `fs_utils.read_text`/`write_text`, 2 MB cap, refuses non-UTF-8 content), `backups`, `core` (ядро + `POST /servers/<id>/core/public` — saves `public_*` fields on `Server`), `public` (`GET /status` — **no login required**, lists `Server` rows with `public_visible=True`) (server-scoped ones all under `/servers/<int:server_id>/...`), plus `auth`, `misc` (also `/servers/<id>/sqltables` and `/servers/<id>/map` — both just render a "В разработке" placeholder template, no logic behind them yet), `api` (`/api/stats` global, `/api/servers/<id>/status` per-server, now includes `status`). Registered in `app/routes/__init__.py`. Server-scoped routes stack `@with_server` under the role decorator and reach the manager via `current_app.server_registry.get(server_id)` (or just `g.server`, same object).
- **`app/__init__.py`** — `create_app(config_class=Config)`: builds the Flask app (with `template_folder`/`static_folder` pointed at the top-level `templates/`/`static/`), initializes extensions, registers the `login_manager.user_loader`, registers blueprints, creates the `ServerRegistry`, runs `db.create_all()` + `ensure_first_admin()`, registers a `context_processor` that exposes `current_server` (== `g.server` if `with_server` ran) to every template, and wires the SocketIO `/server` `connect`/`join` handlers (`join` puts the socket in room `server-<id>`, only for authenticated users).
- **`main.py`** — `app = create_app()` at import time (so `python3 main.py` and any WSGI server importing `main:app` both work); `socketio.run(...)` only under `if __name__ == "__main__"`, with `allow_unsafe_werkzeug=True` (see REVIEW.md 🟠 #13 for why — threading async_mode is deliberate, not an oversight).

File-browsing routes (`/servers/<id>/files/<path:subpath>`) use Flask's real `path` converter (genuine `/` in the URL) — no more `+`-encoding hack. `subpath` is always relative to *that server's* folder, never to the repo root (see the `fs_utils` note above).

Console output reaches the browser two ways: a full-history REST endpoint (`/servers/<id>/console/history`, filtered by `server_id`, `login_required`) for initial page load, and live incremental lines pushed over SocketIO to that server's room. Flask-SocketIO replaces `app.wsgi_app` with its own middleware and intercepts `/socket.io/*` *before* Flask's routing/CSRF machinery ever sees it — keep that in mind if `/socket.io` behavior ever needs touching, CSRF exemptions aren't the mechanism at play there.

Templates all extend `templates/base.html`, which renders the nav bar — a global "Серверы" link always, plus a server-scoped section (Консоль/Игроки/Настройки/Файлы/Бекапы/Ядро, Files/Backups/Core hidden for non-admins) only when `current_server` is set — flashed messages, and auto-injects a CSRF hidden field into every `<form method="post">` on the page via one script block — don't hand-add `csrf_token()` per form, the base template already covers it. Templates gate admin-only controls with `{% if current_user.is_admin %}` (buttons only; the real enforcement is server-side via the decorators above). Styling is one file, `static/css/main.css` (dark glass: translucent `backdrop-filter: blur()` surfaces, acid green/cyan/magenta gradient mesh background, `--gradient-acid` accents), using CSS custom properties; Bootstrap, Google Fonts and the Socket.IO client are pulled from CDNs rather than bundled.
